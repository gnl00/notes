# 事务

> 事务指一组 SQL 语句的集合，集合中的 SQL 语句可能是 `insert/update/select/delete`，这些 SQL 语句作为一个整体执行，保证最后都能成功或者都失败。

## 四大特性

> ACID

1、**原子性**（Atomicity）

事务要么全部提交成功，要么全部失败回滚，不能只执行其中一部分操作

2、**一致性**（Consistency）

- 如果数据库系统在运行过程中发生故障，有些事务尚未完成就被迫中断，未完成的事务对数据库所做的修改已有一部分写入物理数据库，这时数据库就处于一种不正确的状态，也就是不一致的状态。
- 一致性要求操作前后数据总量不变，事务的执行不能破坏数据库的完整性和一致性，一个事务在执行之前和执行之后，数据库必须处于一致性状态。

3、**隔离性**（Isolation）

在并发环境中，并发的事务是相互隔离的，一个事务的执行不能被其他事务干扰。不同的事务并发操作相同的数据时，每个事务内部的操作及使用的数据对其他事务是隔离的，并发执行的各个事务之间互不干扰。

4、**持久性**（Durability）

- 事务提交之后，数据发生的变化是永久的。
- 一旦事务提交，它对数据库中对应数据的变更就会永久保存到数据库中，即使发生系统崩溃或者服务器宕机等故障，只要数据库能够重新启动，就能将其恢复到事务成功的状态。

## 隔离级别

**查看当前隔离级别**

```sql
-- MySQL 8+
show variables like 'transaction_isolation';
-- MySQL 5.7 兼容写法
show variables like 'tx_isolation';
```

**设置隔离级别**

```sql
-- 会话级
set session transaction isolation level repeatable read;
-- 全局级（仅影响新连接）
set global transaction isolation level repeatable read;
```

**并发事务带来的问题**

|            | 概念                                                                                                                                                                   | 产生时机  |
| ---------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------- |
| 脏读       | 一个事务对数据进行了修改，还没有提交修改到数据库，此时另一个事务也访问这个数据，并且读取到了数据，读到脏数据。                                                         | 修改      |
| 不可重复读 | 在一个事务内多次读同一数据，得到的是不一样的结果。事务 A 多次读取同一数据，事务 B 在 A 多次读取的过程中对数据作了更新并提交，导致事务 A 多次读取同一数据时结果不一致。 | 修改      |
| 幻读       | 事务 A 先读取数据，而后并发事务 B 插入或删除了某些数据。事务 A 再次读取发现多/少了某些数据，就像发生了幻觉。                                                           | 新增/删除 |

针对以上问题，**有什么解决办法呢？**

1、加锁。在读取数据前对其加锁，阻止其他事务对数据进行修改；

2、MVCC 多版本并发控制。通过生成某个时间点的一致性数据快照（Snapshot)，并用该快照来提供一定级别的一致性读取（语句级或事务级）。从用户的角度来看，好象是数据库可以提供同一数据的多个版本。

**隔离级别**

1、**读未提交**（*Read Uncommitted*），隔离级别最低，`<u>`存在脏读、不可重复读、幻读`</u>`；

2、**读已提交**（*Read Committed*）

- 读已提交只允许读取已提交的数据，解决脏读，`<u>`存在不可重复读、幻读`</u>`；
- 重点是修改，同样的条件读取数据，发现再次读取出来的值不一样；

3、**可重复读**（*Repeatable Read*），MySQL 默认隔离级别；

- 保证在事务处理过程中，多次读取同一个数据时的结果和事务开始时读取到的结果是一致的。解决脏读和不可重复读；
- 重点是新增或删除。同样的条件，第 1 次和第 2 次读出来的记录数不一样；
- 在 InnoDB 中需要区分：一致性读（普通 `select`）与当前读（`select ... for update` / `update` / `delete`）。当前读通过 next-key lock 等机制避免并发插入导致的幻读。

4、**串行化**，最严格的事务隔离级别，要求所有事务串行化执行。事务只能一个接着一个处理，不能并发执行。脏读、不可重复读、幻读都不存在。

**各隔离级别对比**

| 隔离级别 | 读数据一致性                             | 脏读 | 不可重复读 | 幻读 |
| -------- | ---------------------------------------- | ---- | ---------- | ---- |
| 读未提交 | 最低级别，只能保证不读取物理上损坏的数据 | ✔   | ✔         | ✔   |
| 读已提交 | 语句级                                   | ✖   | ✔         | ✔   |
| 可重复读 | 事务级                                   | ✖   | ✖         | 理论上可能；InnoDB 当前读可通过间隙锁/next-key lock 抑制 |
| 串行化   | 最高级别，事务级                         | ✖   | ✖         | ✖   |

## 事务的实现

> 锁+日志+MVCC

[**原子性与隔离性**](https://juejin.cn/post/7336870259582386195)

### 读写锁

读锁，又称共享锁；写锁，又称排他锁。

- 读锁可共享，多个读请求可以共享一把锁读数据，不会造成阻塞
- 写锁会排斥其他所有获取锁的请求，会一直阻塞，直到写操作完成才释放锁
- 通过读写锁可以做到读读并行，但不能做到读写/写写并行

可重复读不是只靠“读写锁”实现，而是 **MVCC（一致性读）+ 锁（当前读/写）** 共同实现。

### Redo Log

> 重做日志分为重做日志缓冲（*redo log buffer*）和重做日志文件（*redo log file*）。事务执行过程中会持续产生 redo 记录，提交时按刷盘策略保证持久化。

InnoDB 基于 WAL（Write-Ahead Logging）：先写日志，后刷数据页。事务提交时会先把相关 redo 记录写入 *redo log buffer*，再按刷盘策略落盘。

是否会丢失“已提交事务”，关键取决于 redo 的刷盘策略（如 `innodb_flush_log_at_trx_commit`）

- `innodb_flush_log_at_trx_commit = 1`：每次提交都刷盘，最安全，性能开销最大；
- `innodb_flush_log_at_trx_commit = 2`：每次提交写文件系统缓存，刷盘由 OS 定时触发，宕机可能丢最近事务；
- `innodb_flush_log_at_trx_commit = 0`：提交时不强制写 redo，风险更高。

> 实现持久性

使用 *redo log* 来**记录已成功提交事务的修改信息**，并且把 *redo log* 文件持久化到磁盘上，系统重启之后再读取 *redo log* 恢复最新数据，实现**事务的持久性**。

### Undo Log

> 回滚日志，用于记录数据被修改前的信息，为了在发生错误时回滚之前的操作。

InnoDB 在对记录做变更时会生成 undo 记录（insert/update/delete 对应不同 undo），用于回滚与构造历史版本链。

undo 的核心作用不是“替代数据页持久化”，而是支持事务回滚和 MVCC 可见性判断。数据页刷盘与日志刷盘是不同维度的流程。

如果数据库系统出现异常或者事务执行 rollback 操作可以根据 *undo log* 进行回滚，回到修改前的状态。根据回滚日志做逆向操作：

* insert => delete
* update => update
* delete => insert

> 实现原子性

事务执行失败可以使用 *undo log* 来回滚数据，用于**保障事务的原子性**。

### MVCC

MVCC（*Multi Version Concurrency Control*），多版本并发控制。

> MySQL 基于提升并发性的考虑，大多数事务型存储引擎实现都不是简单的行级锁，一般都实现了多版本并发控制（Oracle/PostgreSQL 也有相应的实现，只是实现机制不相同）。

MVCC 让一致性读（`select`）尽量不加锁；当前读（`select ... for update` / `select ... for share`）和写操作（`insert/update/delete`）仍然依赖锁机制。

> MVCC 主要用于读已提交（RC）和可重复读（RR）的**一致性读**。为什么呢？
>
> RC：通常每条一致性读语句都会创建新的 `read view`，因此同一事务内前后两次查询可能看到不同已提交结果。
>
> RR：事务内首次一致性读创建 `read view`，后续一致性读复用这个视图，因此可重复读。
>
> RU：可以读到未提交版本，不依赖 MVCC 的一致性可见性规则；串行化主要依赖严格加锁/调度。

MVCC 存在的不足之处是每行记录都需要额外的存储空间。以 InnoDB 为例，记录中常见的隐藏字段包括：

* `DB_TRX_ID`：最后一次修改该行的事务 ID；
* `DB_ROLL_PTR`：指向 undo 日志记录，用于回溯历史版本；
* `DB_ROW_ID`：在没有显式主键时由 InnoDB 生成的隐藏主键。

MVCC 在 MySQL 中的实现需要依赖 *undo log* 和 *read view*：

* *undo log*，保存旧版本链，提供回滚与历史快照版本；
* *read view*，决定当前事务能看到哪些快照版本。

> MVCC 配合锁机制实现隔离性。

事务的**隔离性**通常由**MVCC（一致性读）+ 锁机制（当前读/写）**共同实现；

> 事务的一致性由：持久性 + 原子性 + 隔离性来实现。

实际上，一致性是最终目标，不是某一个机制单独提供的。
- ACID 里的 Consistency（C）是“满足约束和业务不变量”的目标，不只是机制相加。
- A/I/D 只能提供基础保障，仍需：
  - 业务规则、约束（唯一键/外键/check）；
  - 正确的应用逻辑和并发控制；
  - 复制一致性、故障恢复、操作流程（DDL/DML 变更策略）。
所以 C 是系统性结果，不是单机内核机制的简单求和。

## MDL(Metadata Lock) 元数据锁

MDL（Metadata Lock）用于保护表元数据一致性。MySQL 在访问表时会自动加 MDL：

- DML（`select/insert/update/delete`）通常持有 MDL 读锁；
- DDL（`alter/drop/rename`）需要 MDL 写锁；
- 读锁与写锁冲突，长事务中的 DML 很容易阻塞后续 DDL。

**典型现象**

- `alter table ...` 一直等待；
- 业务侧大量普通 SQL 正常，但 DDL 长时间不返回；
- `show processlist` 看到 DDL 处于 `Waiting for table metadata lock`。

**排查命令（MySQL 8）**

```sql
-- 1) 看正在执行的会话
show processlist;

-- 2) 看元数据锁持有与等待关系
select
  l.OBJECT_TYPE,
  l.OBJECT_SCHEMA,
  l.OBJECT_NAME,
  l.LOCK_TYPE,
  l.LOCK_DURATION,
  l.LOCK_STATUS,
  t.PROCESSLIST_ID,
  t.PROCESSLIST_USER,
  t.PROCESSLIST_HOST,
  t.PROCESSLIST_INFO
from performance_schema.metadata_locks l
join performance_schema.threads t
  on l.OWNER_THREAD_ID = t.THREAD_ID
where l.OBJECT_SCHEMA is not null
order by l.OBJECT_SCHEMA, l.OBJECT_NAME, l.LOCK_STATUS;
```

**`alter table` 一直 pending 的排查方案**

1. 先确认是否 MDL 阻塞

```sql
show processlist;
-- 重点看 DDL 线程的 State 是否为：
-- Waiting for table metadata lock
```

2. 定位“谁在等、谁持锁”

```sql
select
  w.PROCESSLIST_ID   as waiting_pid,
  w.PROCESSLIST_USER as waiting_user,
  w.PROCESSLIST_INFO as waiting_sql,
  b.PROCESSLIST_ID   as blocking_pid,
  b.PROCESSLIST_USER as blocking_user,
  b.PROCESSLIST_INFO as blocking_sql,
  l.OBJECT_SCHEMA,
  l.OBJECT_NAME,
  l.LOCK_TYPE,
  l.LOCK_STATUS
from performance_schema.metadata_locks l
join performance_schema.threads w
  on l.OWNER_THREAD_ID = w.THREAD_ID
left join performance_schema.metadata_locks bl
  on l.OBJECT_SCHEMA = bl.OBJECT_SCHEMA
 and l.OBJECT_NAME = bl.OBJECT_NAME
 and bl.LOCK_STATUS = 'GRANTED'
 and bl.OWNER_THREAD_ID <> l.OWNER_THREAD_ID
left join performance_schema.threads b
  on bl.OWNER_THREAD_ID = b.THREAD_ID
where l.LOCK_STATUS = 'PENDING'
order by l.OBJECT_SCHEMA, l.OBJECT_NAME;
```

3. 找“阻塞会话是否为长事务未提交”

```sql
select
  trx_mysql_thread_id,
  trx_started,
  trx_state,
  trx_operation_state,
  trx_rows_locked,
  trx_query
from information_schema.innodb_trx
order by trx_started;
```

4. 处置顺序（先业务安全，后技术动作）

- 确认能否提交/回滚当前事务；
- 若无法快速处理且影响面大，评估后执行 `kill <blocking_pid>;`；
- 避免直接 kill DDL 线程，优先解除阻塞源（持锁会话）。

5. 复盘与预防

- 控制事务生命周期，避免“长事务 + 空闲连接不提交”；
- DDL 放低峰执行，必要时拆小批次或采用在线变更方案；
- 变更前先检查是否存在长事务与热点写入。
